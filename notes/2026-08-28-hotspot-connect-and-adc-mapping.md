# 手机热点连接服务器失败与 ADC 通道错误

## 现象

连接 vivo S16 Pro 热点后，信号约 -31dBm，获得 192.168.105.29，但连接 4.197.40.220:8000 的 TCP 探测失败，反复显示 Server unavailable。电池每秒报告约 38～136mV 无效值。

## 排查过程

- 日志未进入鉴权/MQTT 阶段，失败发生在 TCP 建连，不能归因为 UDP 或唤醒模型。
- 本机沙箱外访问既有 /health 接口返回 HTTP 200，但本机网络不等同于设备热点网络。
- 本地 Xtensa errno.h 定义 113 为 ECONNABORTED，不是 Linux 上同号的 EHOSTUNREACH。
- 原探测使用阻塞 connect，SO_RCVTIMEO/SO_SNDTIMEO 未实现预期 5 秒建连截止，日志实际等待约18秒。
- 本地 ESP-IDF adc_channel.h 显示 GPIO1 对应 ADC1 channel0；原代码直接把 GPIO1 强制转换为 channel1，实际读 GPIO2。
- 查阅既有网络调试笔记。AGENTS 指定的 macOS 小智参考路径在本机不存在。

## 根因与边界

在线唤醒不可用的直接原因是未建立服务器连接。热点移动网络、路由、端口策略或当时服务器状态的具体责任尚不能仅凭日志确定。ADC 通道映射错误是独立且确定的固件问题，先前仅滤波不能解决读错通道。

## 解决方案

- 使用 nonblocking connect + select + SO_ERROR，使 TCP 探测最多等待5秒，记录错误码及文本。
- Overlay 改为 WiFi connected / Server connection failed，避免把连接失败直接表述为服务器宕机。
- 使用 adc_oneshot_io_to_channel 映射 GPIO 到 ADC 单元/通道，并用于配置、校准和读取。
- 检查 ADC 读取和校准返回码。无效值日志改为首次及每30次打印，并打断低电连续计数。
- 未改服务器地址、端口、防火墙或凭据。

## 后续验证

电脑连接同一热点后执行 Test-NetConnection 4.197.40.220 -Port 8000，以及 curl.exe --connect-timeout 5 --max-time 8 http://4.197.40.220:8000/health。与原 Wi-Fi 对比。HTTP 恢复后再验证鉴权返回的 MQTT 端口及 UDP 音频，不应提前判断 UDP 被阻断。

## 教训

区分 Wi-Fi 链路和公网服务器连通性；固件 errno 应查目标工具链而非套用桌面 Linux。GPIO 编号不是 ADC 通道编号。电池仍须真机确认 GPIO1 确实连接了预期分压电路，不能仅凭软件映射断言电量准确。

## 后续日志复核

新附件显示设备约12.724秒发起 TCP 探测、17.727秒返回 errno=116 (Connection timed out)，第二次47.744～52.750秒也同样超时，说明5秒截止逻辑生效，但公网路径仍未打通。热点首次关联曾失败，随后成功拿到IP，后续日志没有持续断连。

只读检查发现电脑 WLAN 为192.168.1.21、以太网为192.168.1.9，网关均为192.168.1.1；设备热点网关为192.168.105.69。电脑再次访问健康接口返回200，但不是同一路径测试。下一步须让电脑接入同一热点，并临时断开以太网/其他出口，确认网关后测试8000端口。未授权自动改变电脑网络配置，因此本轮没有断开网卡，也没有更改或重建固件。

电池映射修正后仍出现62～88mV，不能再仅归因通道编号；需要确认板级电池分压是否接在GPIO1以及分压比例。此告警与服务器TCP超时独立，不能把无效ADC值当作真实剩余电量。
